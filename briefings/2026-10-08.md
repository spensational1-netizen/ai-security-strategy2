## 1. Coverage-gap flag: AWS AgentCore Harness default-shell-tool credential exfiltration via prompt injection — Spencer's call on backdating

Palo Alto Networks Unit 42 published this research Sept 18, 2026 (a Cloud Security Alliance note followed Sept 19) — missed in daily coverage at the time; this is the largest coverage lag caught to date, roughly three weeks. Unit 42 found that Amazon Bedrock AgentCore Harness ships with a built-in shell tool enabled by default in every session, running as root, that can reach into the same memory space where credentials are resolved to plaintext. In their demonstration, a single support ticket with hidden instructions was enough: indirect prompt injection steered the agent into executing a shell command, reading the harness runtime's process memory, locating a live JSON Web Token, and exfiltrating it to an attacker-controlled endpoint — all without the attacker ever holding AWS credentials.

AWS reviewed the disclosure and closed it as informative under the AgentCore shared-responsibility model, pointing to customer-side allowedTools scoping and egress filtering as the mitigation rather than shipping a code fix or assigning a CVE. This is distinct from a separate, already-patched AgentCore Harness bug (CVE-2026-18830, an authenticated tool-use-injection flaw fixed server-side before July 31) — that one got an AWS-side fix; this one did not.

- Source: [Unit 42 (Palo Alto Networks)](https://unit42.paloaltonetworks.com/securing-aws-agentcore-harness-credentials/), [Cybernews](https://cybernews.com/security/aws-agentcore-platform-credential-leak/), [Cloud Security Alliance](https://labs.cloudsecurityalliance.org/research/csa-research-note-aws-agentcore-credential-exfiltration-2026/)
- **Why this matters:** This is a close mechanism match to the existing DeepSeek Harness precedent already in Row 6 (an agent harness's own control surface abused to reach privileged access — both are literally named "Harness" products) but via indirect prompt injection rather than a direct unauthenticated API call, with credential theft as the payload rather than sandbox-disable. AWS's shared-responsibility closure — no code fix, no CVE — is itself a notable vendor-response data point, echoing the kind of disclosure-practice scrutiny already tracked in Section 7, though it's not being proposed as its own Section 7 edit here.
